#+title: Bugs
* TODO drafts are not saved to the drafts folder but instead in the current folder
* CLOSED 'c' to save attachments hangs until the full-walk finishes

Report: "something hangs after I press 'c' to save attachments." Root
cause: ONE notmuch worker served both the long full-walk reads (refresh
full-reloads ~1.4-3.5s, search tabs) and the interactive ops (categorize,
open). The walk held the single handle, so categorize's ActQueryMsgs +
ActSnapshots queued behind it.

Fix (6b05568): walks moved to a dedicated second worker with its own
backend handle; interactive ops never queue behind a walk. The walk
handle reopens (Backend.Reopen / ActReopen, cgo:
notmuch_database_reopen; CLI: no-op) before each cycle and search so it
stays current with the interactive worker's writes. Regression:
src/app/walkworker_test.go TestWalkWorkerSplit - categorize completes
while the walk backend blocks; a reversion to one shared worker fails it.

* CLOSED opening a message from a search tab fails until the walk merges it

Report: "search a query, open another tab, press 'c', then open a message
- it opens in the inbox tab instead of the current view" and "when I
press c it takes a while before I'm allowed to open a view."

Root cause: in a flat search tab the cursor yields the SYNTHETIC thread
id (= the message id, groupThreads src/app/refresh.go). The open
resolves rows-first from the views (threadFromViews) - but until the
search walk has merged that message, no view holds it, so the open falls
back to ActThread(thread:<msgid>), and notmuch's thread: operator
matches NOTHING for a message id (proven against the live DB:
count thread:<msgid> = 0, count thread:<real-thread-id> = 1). The empty
fetch rendered as "no messages in thread" (mail.RenderThread on an empty
set), and the TUI's ThreadLoaded error branch drops the pager silently
(src/tui/model.go onThreadLoaded) - so pressing enter did nothing until
the walk happened to merge that message. That is the "wrong tab" and the
"takes a while" delay: repeated enters silently failed until the search
fill reached the cursor message. Unrelated to the Lua categorize script
(the script is fast; the delay was the open failing, not Lua hanging).

Fix: the open/attachment fallback (fetchMsgs, src/app/app.go) tries
thread:<tid> first, and when it comes back empty for a message-id
carrying open, resolves the message by id (ActSnapshots) instead of
failing. A flat-view open now works instantly regardless of the search
walk's merge state. The threaded fallback path is unchanged (ActThread),
so the pinned TestOpenThreadRowsFirst still holds. Regression:
src/app/open_flat_test.go TestOpenFromFlatSearchTabUnmerged - the
faithful fake models thread:<msgid> = 0 and asserts the open renders the
message, not "no messages in thread".

* OPEN self-sent mail (account A to account B) is one notmuch message, deleting moves only one of its files

Scenario: send from an address at account A to your own address at account B (the
classic self-test or a cross-account forward of your own mail). notmuch links the
fcc copy (in A's Sent folder) and the received copy (in B's INBOX) by Message-ID
into ONE message with TWO paths. In the index they are one thread. Delete it.

Current behavior: the apply path resolves the physical move in
`moveEntries` (src/app/apply.go) with `filter.AccountOf(cfg, paths)`
(src/filter/filter.go), which returns the FIRST path's account - one account
for the whole message. The deleted-folder candidates resolve for that one
account, and the mover's Entry carries a single Account/Folder for ALL of the
message's paths. The other account's file is not moved to its own deleted
folder: it is either left behind, or moved toward the wrong account's folder
space.

Why it is hard: the R2 tag model says one message, one home - a single
folder tag (+deleted) is the winner. The physical truth is one message,
multiple files, multiple homes. To move each file correctly the resolution
must be per-FILE per-ACCOUNT: each path under A's prefix goes to A's deleted
folder, each path under B's prefix to B's. That means the move can no longer
be one Account/Folder per message; it must fan out across the message's
paths.

Open questions (unsolved):
- Should BOTH copies move to their respective deleted folders, or only the
  received copy (keeping the sent record in A's Sent folder)? Deleting the
  sent record removes the proof of sending.
- How to express the fan-out: split the message's paths into one Entry per
  account, or make the Entry carry a per-path folder map?
- After the moves, the message keeps +deleted. If both files move, no file
  remains in a live folder - is that the wanted end state? If only the
  received copy moves, the message still has a file in A's Sent folder:
  should it keep +deleted or revert to +sent?
- The single-home tag cannot express per-account state; the move must derive
  it from the paths without contradicting the tag model.
- The same issue applies to any self-addressed thread (reply/forward to
  yourself across accounts).

Pointers: src/app/apply.go `moveEntries` + `AccountOf`, src/filter/filter.go
`AccountOf`, src/filter/mover.go, AGENTS.md R2 (one message, one home).

* OPEN cursor movement is buggy while the F display filter is active

Report: "moving around while 'F' capital F filter is running is buggy." The F
filter is the live display filter (src/tui/model.go ~1498): the prompt calls
`activeView().SetFilter(text)` + `m.rows = Rows()` on every key, esc/enter
keep or restore the text, and the view narrows to the in-memory rows matching
a case-insensitive substring over author, subject, and tags (core/view.go
`SetFilter` + `rowMatches`). It is display-only and synchronous - no async
query - so "running" means while the prompt is open AND/OR while the filtered
rows are active.

Verified so far (scratch tests, src/tui/zz_scratch_filter_test.go - removed):
- Flat (non-windowed) single-message-thread view: j/k through the filtered
  set moves correctly (0 -> 1 -> 2, clamped at the last row). The filtered/
  full index mapping in SetCursorIndex / CursorRowIndex (core/view.go) is
  consistent, and a cursor the filter hides falls back to the first visible
  row.
- The movement code (moveCursor / cursorStepAt / windowSlideAt /
  pageAtEdgeAt in src/tui/model.go) operates in filtered space and mostly
  self-corrects indexOffset via the render clamp.

Suspects (NOT yet reproduced end to end):
- Windowed threads (default `[index.thread] max-rows = 10`): ghosts ("+N
  more") are dropped by rowMatches (nil Msg -> false), so only matching rows
  from the current window chunk are visible. Crossing a thread boundary calls
  SlideWindow (core/view.go), which slides the FULL thread's window and
  re-derives a DIFFERENT filtered subset - the visible rows can jump under
  the cursor mid-move. The scratch windowed fixture collapsed to a single row
  instead of the expected window+ghosts (itself suspicious, undiagnosed).
- A background refresh while the prompt is open (ViewDiff -> EventMsg ->
  `m.rows = Rows()` at src/tui/model.go ~870) re-materializes under the
  mid-typed filter; m.indexOffset can be stale against the new filtered set.
- The filter prompt captures j/k as typed text while open (expected prompt
  behavior), but a user expecting movement sees the list jump as the filter
  re-narrows - possibly the reported "buggy moving".

Open questions (unsolved):
- Is the report the windowed-thread jump, the refresh-under-prompt remap, or
  the prompt-captures-keys expectation? Needs the user's exact repro (filter
  text, thread depth, whether a sync/refresh was running).
- Should the display filter suppress window sliding (pin the thread window
  while a filter is active) so movement stays inside the filtered subset?

Pointers: src/tui/model.go `moveCursor`/`windowSlideAt`/`SetFilter` prompt
(~1498), src/core/view.go `SetFilter`/`rowMatches`/`SlideWindow`/`SetCursorIndex`
(~325, ~650, ~736), src/tui/model.go EventMsg rows rematerialize (~870).

* CLOSED html inline layout is O(n^2) on one unbroken token (content-reachable hang)

A single long unbroken token (base64 blob, long URL, crafted mail) makes the
stage-1 inline layout quadratic in two independent places:

- atomizeText collapse mode grows a word one rune at a time:
  `out[n-1].text += string(r)` (src/lib/html/inline.go ~106-107). Strings are
  immutable, so every append copies the whole accumulated word - O(n^2) byte
  copies for an n-rune token. Every collapse-mode text leaf hits this
  (normal/nowrap/pre-line), i.e. most mail.
- cutText (src/lib/html/inline.go ~303-310) re-measures from the string head
  on every rune (`m.Width(s[:i+n])`): O(n) per step, O(n^2) total. This runs
  on normalize's emergency char-break (overflow-wrap:anywhere) of an over-wide
  token, so normalize over a giant preserved or collapsed run is quadratic too.

A multi-hundred-KB unbroken word stalls the render for minutes. Mail HTML
reaches this path on the read surface.

Fix (Plan 3 Task 1 + 1a): atomizeText accumulates collapse-mode words in a
strings.Builder and flushes an atom at a separator (c772a78); cutText carries
a running px width through the RuneStepper interface instead of re-measuring
from the head (c772a78); the preserved-wrap fill tracks a running remainder
width and breakAtSpace stops measuring past the budget (72111bd, 781ab59,
83cb18e). Regression: TestGiantUnbrokenTokenLaysOutLinearly,
TestPreservedSpaceDenseTokenLaysOutLinearly, TestCutTextDoesNotRescanFromHead,
TestBreakAtSpaceStopsMeasuringPastBudget, TestPreservedWrapFillDoesNotRescanRemainder,
TestCharBreakMeasuresPxNotRunes (double-width runes prove px, not rune count).

Pointers: src/lib/html/inline.go atomizeText, cutText, LayoutInline charBreak.

* CLOSED scheduled list sorts the display-time string, not the send time (misorders across weekday boundaries)

Report: TestScheduledList (src/app/schedule_test.go:315) fails nightly ~22:00-23:00
local and passes the rest of the day. It schedules two mails at now+1h and now+2h and
asserts the s-key list sorts by send time (earlier first).

Root cause: scheduledList (src/app/schedule.go:131) parses each spool record's RFC3339
send time (line 145), then formats it to the DISPLAY string "Mon Jan 2 15:04" (line
150) and sorts THAT lexicographically (line 153). The weekday name leads the sort key,
and weekday names are not chronological under string order ("Fri" < "Thu", "Mon" <
"Sun", and the week cycles anyway), so any two pending mails whose formatted weekday
differs misorder. The test only passes when both target times share a weekday: the
failure window is ~22:00-23:00 (+1h stays today, +2h crosses midnight -> "Fri Sep 4
00:15" sorts before "Thu Sep 3 23:15" because "Fri" < "Thu"). The same comparator
misorders across month ends, year ends, and any opposite-weekday pair, so it is wrong
well beyond the nightly window - the clock only decides when the existing test trips.

Fix (7e2fdb3): scheduledList sorts on the parsed time.Time (parallel ats
slice, ats[i].Before(ats[j])); the display string is emitted after the sort.
Regression: TestScheduledList (unchanged, src/app/schedule_test.go:315) - it
failed nightly ~22:00-23:00 and now passes year-round, catching any return to
string-keyed sorting.

Pointers: src/app/schedule.go scheduledList (145-155); src/app/schedule_test.go:315
TestScheduledList.

* OPEN html tables: captions are built but not rendered (stage-1 deferral)
The box tree builds caption boxes and the grid readers skip non-conforming
children, but no flow case emits a caption row: weasyprint paints the caption
above (or below) the table in the block flow, stage 1 never does. Caption
rendering is an explicit non-goal of plan 4; a later table plan or stage 2 owns
the caption-as-a-block-row emission. Pointers: src/lib/html/table.go buildGrid
(skips non-conforming children), plan 4
(docs/superpowers/plans/2026-09-03-html-tables.md) self-review notes.

* OPEN html tables: intra-cell block vertical margins are flattened inside a grid row
A grid row is one flat strip shared across cells, so the collapsed margins
between a cell's block children are zeroed (cellRows sets Gap = 0 on every
LayoutBlock row): weasyprint gives the cell its full block-flow vertical rhythm.
Unrepresentable while a strip is shared; stage 2's quantizer or a later table
plan could re-introduce cell-internal rhythm by splitting strips. Pointers:
src/lib/html/table.go cellRows.

* OPEN html tables: a colspan never mints empty spacer columns beyond the row's cell count
Column count is the widest row by cell count, so a colspan is clamped to the
free columns remaining in the row and never builds empty spacer columns;
weasyprint would create them from a colspan attribute alone. This is the O(n)
clamp - a huge colspan attribute cannot mint a huge grid. Pointers:
src/lib/html/table.go buildGrid (doc).

* OPEN html tables: author display:table-* on a non-table element renders as block, not a grid
RoleTable is gated to real table-family tags (Task 1a): a div with
display:table (or a display:table-cell remap) demotes to RoleBlock and flows as
plain blocks, where weasyprint anonymous-repairs it into a grid. x/net/html
cannot nest a real table into that shape, it is not a mail pattern, and a
normalizer for non-HTML5 DOM sources would be the future opt-in. Pointers:
src/lib/html/box.go role gate (~147-150), plan 4 Task 1a conformance.

* OPEN html images: px height never advances the vertical stream (stage-1 deferral)
Rows are terminal-height strips with no line-box height, so an image's used
uH is carried on the box for stage 2 and does not push later rows down;
weasyprint grows the line box. Fine for the terminal (a stage-2 image block
reserves its own rows); a PDF backend would need line-box height. Pointers:
src/lib/html/img.go usedImg, src/lib/html/block.go Row.

* OPEN html images: an inline image shares its text line (stage-1 deferral)
A <p>x<img>y</p> lays the image on the x/y line (weasyprint-faithful). The
mail walker renders every image on its own line; stage 2 (the plan-6
quantizer) decides terminal own-row emission, which must split the line
around the image atom. Pointers: src/lib/html/inline.go LayoutInline img
dispatch, plan 5 decisions.

* OPEN html images: a broken or unloadable image lays out at zero width
An img with no loadable src and no CSS width has no intrinsic, so it emits a
zero-width row; weasyprint paints the alt text and a broken-image box. Alt
text is a stage-2 render choice (the walker today drops it too). Pointers:
src/lib/html/img.go ResolveImages/imgExtentW, plan 5 decisions.
